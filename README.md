# Codecrafter's Grimoire

A project-based Python course that runs entirely in the browser. Read the
lesson, write the code, run it, and see what it actually did.

81 projects across 20 modules and three acts, each with a brief, three tiers of
hints, a starter, a hidden test suite and a reference solution. Python really
executes: [Pyodide](https://pyodide.org) (CPython 3.14 compiled to WebAssembly)
runs in a web worker, so there is no server and nothing to install. Everything,
including the spreadsheet and PDF libraries, is served from the app itself. It
makes no network request once the page has loaded.

## Playing

# Codecrafter's Grimoire

[Launch the Live Interactive Grimoire](https://shaunbeach.github.io/Codecrafters_Grimoire/)

You start on the Quest Map. Each module is a region of the world; each project
is a standing stone on the road through it. A stone is dark until the one
before it is passed, amber when it is open, and green once you have passed it.
The map's list view shows the same projects with the same state, and is the
default if your system asks for reduced motion.

Open a project and you get a brief on the left, the editor on the right, and
the Stage beneath it.

- **Run** executes your file and shows what happened: console output, any
  files it created or changed (a spreadsheet comes back as a grid with the
  changed cells marked), any image it drew. Run as often as you like; it does
  not grade.
- **Check** runs the hidden test suite. Pass it and the next stone opens.
- The wizard watches quietly. After three failed checks he offers a hint;
  there are three tiers, from a nudge to most of the answer. Hints are never
  forced on you.
- `input()` really blocks: the program pauses until you type a line into the
  terminal.
- **Notes** are per project and autosave. **Your Grimoire** collects every
  note in course order and exports them as one Markdown file.
- **Free roam** at the bottom of the map opens every project at once.

Keyboard: `Cmd/Ctrl+Enter` runs, `Shift+Cmd/Ctrl+Enter` checks, `Escape` returns
to the map. Everything is operable without a mouse.

Progress, code and notes live in your browser's storage. Nothing leaves your
machine.

| II, The Artisan | Ink and Parchment, When Things Break, Living Things, Memory | 19 |
| III, The Archmage | Distant Voices, Scrying the Network, Spreadsheets, Phantom Hands, Decoding the Bureaucracy, The Interchange, The Painted Sigil, The Deep Index, The Speaking Frame, The Trial | 32 |

Act I teaches syntax as magic, in a forest. Act II moves to craft, in a forge
among ruins. Act III drops the metaphor: the network, the filesystem and the
screen turn out to be the uncanny things, and the world becomes a crystalline
archive.

## Running it locally

Requires Node 20.19 or newer.

```bash
npm install     # also downloads the Python runtime and fonts into public/ (about 19 MB, once)
npm run dev     # http://localhost:5173
```

```bash
npm run build
npm run preview # http://localhost:4173
```

## Hosting

The build in `dist/` is static. Two things to know:

**Subpaths.** If the site is served from a subpath (GitHub Pages without a
custom domain serves `https://user.github.io/repo/`), set the base path when
building:

```bash
BASE_PATH=/repo/ npm run build
```

**Headers.** The blocking terminal needs the page to be cross-origin
isolated, which normally means the host sends two headers:

```
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp
```

Hosts that cannot set headers, GitHub Pages included, still work: the page
loads [coi-serviceworker](https://github.com/gzuidhof/coi-serviceworker)
first, which registers a service worker that adds the headers to every
response and reloads the page once. After that first visit the terminal blocks
on `input()` exactly as it does locally. On a host that already sends the
headers the script does nothing.

**GitHub Pages.** `.github/workflows/deploy.yml` builds and publishes on every
push to `main`. It runs `npm ci` (which vendors the Python runtime), builds
with `BASE_PATH` set from the repository name, and deploys `dist/`. Enable
Pages in the repository settings with "GitHub Actions" as the source. If you
attach a custom domain, set `BASE_PATH` in the workflow to `/`.

`public/pyodide/` and `public/fonts/` are generated by `npm install` and are
not committed, so a deploy pipeline must run `npm ci` before `npm run build`.

## How it is built

React 19, TypeScript, Vite 8 and Tailwind 4. No backend.

```
src/runner/         the Python engine: worker, harness, packages, stand-ins
src/course/         acts, modules and projects
src/course/modules/ one folder per module, one per project
src/components/     map, workspace, stage, wizard, notes
src/storage/        progress in localStorage; drafts and notes in IndexedDB
scripts/            verification and asset vendoring
```

**The runtime** runs the learner's code in a worker. `Run` executes the file;
`Check` imports it as a module and runs the suite, so an
`if __name__ == "__main__":` block at the bottom of your file behaves exactly as
it would in real Python. Every run starts from an empty workspace. Afterwards
the workspace is diffed and every changed file is decoded in Python and sent to
the page as JSON; only images cross as bytes.

**Packages.** `openpyxl`, `pypdf` and `python-docx` are vendored as wheels.
`pyautogui` and `pyperclip` are stand-ins that record what your program would
have done, since a browser cannot move a real mouse. Anything else in Pyodide's
lockfile loads on demand when a project declares it.

**The map** is a Canvas 2D scene: three procedurally painted, seeded worlds with
depth-scaled scenery, pointer parallax and particles. The stones on it are real
buttons layered on top, so keyboards and screen readers never see the canvas.

**Loading.** The map is the only view in the entry chunk (under 100 kB gzipped).
The editor, the markdown renderer and the Python worker load when a project
opens; course content loads one module at a time. Each module folder has a
generated `content.ts` (`npm run gen:content`) that makes this split possible.

## Verifying

```bash
npm run runtime-check    # the engine itself
npm run verify           # every solution passes, every starter fails, no fixture leakage
npm run check:bundle     # the shape of dist/ (after npm run build)
npm run check:timeout    # an infinite loop is stopped and the runner recovers

npm run dev &            # the next four drive a real browser
npm run verify:browser   # all 81 projects through the real worker, network blocked
npm run shell-check      # map, wizard, stage and notes end to end
npm run check:a11y       # keyboard journeys; map and list view agree
npm run slice-check      # the spreadsheet grid and the blocking terminal

npm run build && npm run preview &
npm run check:prod       # the built app: what loads when, and the worker boots
```

`verify` runs every suite twice in the same workspace, because a suite whose
tests mutate a shared fixture passes once and then quietly changes meaning.
`verify:browser` blocks every request that leaves the origin, so an accidental
CDN dependency fails the build rather than a learner on a plane.
